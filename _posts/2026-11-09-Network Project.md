## 개요

네트워크 프로젝트에서 개발한 무선 네트워크 공격 탐지 도구 DART(Deauthentication Attack Recognition Tool)의 기획 배경과 시스템 구조, 공격 탐지 방식을 정리했다. 그중 직접 담당한 Event Handler의 비동기 이벤트 처리, 로그와 경보 생성, 구성요소 오류 처리를 중심으로 구현 내용을 소개하고, 팀의 검증 결과와 프로젝트를 통해 배운 점을 담았다
</div>

## 1. 프로젝트 기획 배경

Deauthentication 프레임은 802.11 무선 네트워크에서 정상적인 연결 종료에 사용하는 관리 프레임이다. 하지만 보호가 충분하지 않은 환경에서는 위조된 프레임을 보내 클라이언트의 연결을 강제로 끊는 공격에 악용될 수 있다.

이때 Deauth 패킷의 개수만으로 공격을 판단하면 한계가 생긴다. 정상적인 연결 종료를 공격으로 오인할 수 있고, 적은 수의 패킷을 지속적으로 보내는 공격은 놓칠 수도 있다. 송신자 주소만으로 정상 AP와 위조 송신자를 구분하기도 어렵다.

DART는 BSSID별로 패킷을 묶고 재전송된 중복 프레임을 제거한 뒤, 짧은 시간에 연속적으로 발생하는 Deauthentication 프레임의 패턴을 분석하도록 구현했다. 현재 점수 계산에는 최대 Burst의 프레임 수를 사용하며, RSSI나 Reason Code를 조합하는 방식은 적용하지 않았다.

## 2. 개발 환경과 시스템 구조

주요 개발 환경은 다음과 같다.

| 구분          | 사용 기술                   |
| ----------- | ----------------------- |
| 운영체제        | Kali Linux              |
| 무선 패킷 수집 환경 | mac80211 / Monitor Mode |
| 개발 언어       | Python                  |
| 패킷 수집 및 파싱  | Scapy                   |
| 검증 데이터셋     | AWID3                   |
| 데스크톱 UI     | Tkinter                 |
| 배포 형태       | `.deb` 패키지              |

핵심 탐지 흐름은 Packet Capture, Detector, Event Handler로 구성했다. Event Handler가 생성한 기록은 Desktop UI에서 조회하고, 알림은 Notification Bridge를 통해 사용자 세션에 전달한다.

```text
Packet Capture → Detector → Event Handler
                                  ├─ 공격 기록 → Desktop UI에서 조회
                                  └─ 알림 → Notification Bridge → 데스크톱 알림
```

Packet Capture는 무선 패킷을 수집하고, Detector는 Window별 탐지 점수와 상태를 생성한다. Event Handler는 탐지 결과를 집계해 공격을 확정하고 기록과 알림을 처리한다. Desktop UI는 감시 서비스의 시작을 요청하고 저장된 공격 기록을 보여준다.

## 3. DART의 공격 탐지 방식

### 패킷 수집과 정규화

Monitor Mode 인터페이스에서 수집한 패킷을 탐지에 사용할 공통 형식인 `NormalizedEvent`로 정규화한다. 이 데이터에는 캡처 세션 식별자, 패킷 식별자, 이벤트 시각, 프레임 유형과 Subtype, 송신·수신 MAC 주소, BSSID, Sequence Number, Retry 여부가 포함된다.

Detector는 이 중 Management Frame의 Subtype 12인 Deauthentication 프레임을 선별한다. 동일한 송신·수신 MAC 주소, BSSID, Sequence Number를 가진 프레임이 Retry로 다시 들어오면 중복으로 처리해 Burst 계산에서 제외한다.

### Window와 Burst 기반 시계열 분석

수집한 패킷은 개별 패킷 단위로만 판단하지 않고 일정한 시간 구간으로 묶어 분석한다.

- **Window size 0.5초:** 한 번의 분석에 사용하는 시간 구간
- **Window stride 0.25초:** 분석 구간을 이동하는 간격
- **Burst gap 0.1초:** 연속된 패킷을 하나의 Burst로 묶는 기준

이 구조를 통해 짧은 시간에 연속적으로 발생하는 패킷 집단을 파악하고, 단발성 패킷과 반복적인 발생 패턴을 구분한다.

### 점수 기반 상태 판정

Detector는 각 Window의 패킷을 BSSID별로 묶고, 재전송 중복을 제거한 Deauthentication 프레임에서 가장 큰 Burst의 크기를 구한다. 점수는 다음과 같이 계산한다.

```text
탐지 점수 = min(최대 Burst의 프레임 수 / 3, 1.0)
```

점수가 0.3 미만이면 `NORMAL`, 0.3 이상 0.6 미만이면 `WARNING`, 0.6 이상이면 `ATTACK` 후보로 분류한다. 여기서 `ATTACK`은 Window별 후보 상태이며, 제품 실행 시 최종 공격 확정과 공격 상태 관리는 Event Handler가 담당한다.

현재 선택된 파라미터는 최근 1초 동안 필요한 ATTACK 후보 수가 1개이므로, 해당 시간 범위에 후보가 한 건 이상 있으면 공격 확정 조건을 만족한다. 이 기준값은 파라미터 튜닝 결과를 제품에 반영한 것이다.

## 4. 내가 구현한 Event Handler

Event Handler는 **탐지 결과를 실제 공격 상태와 사용자 알림으로 연결하는 계층**이다. Detector의 Window별 점수를 다시 계산하지 않고, 전달받은 후보를 집계해 공격을 확정하고 기록 저장, 알림 전달, 오류 처리를 수행하도록 구현했다.

### 탐지와 후속 처리의 역할 분리

Detector는 Window별 상태와 점수, 원본 Deauthentication 프레임 수, 중복 제거 후 프레임 수, 중복 Retry 수, 최대 Burst 크기를 담은 `DetectionResult`를 생성한다.

Event Handler는 이 결과를 전달받아 캡처 세션인 `source_id`별로 공격 상태를 관리한다. BSSID는 공격 기록에 남기는 그룹 정보이며, 시스템의 공격 상태는 BSSID별로 따로 관리하지 않는다.

이렇게 역할을 나누어 Window별 탐지 규칙과 공격 확정 이후의 기록·알림 처리를 구분했다.

### Queue를 통한 비동기 이벤트 처리

탐지 결과는 Queue를 통해 전달받도록 구현했다.

```text
Detector에서 탐지 결과 생성
            ↓
       Queue에 전달
            ↓
Event Handler에서 순차적으로 처리
            ↓
  기록 저장 및 Bridge로 알림 전달
```

로그 저장이나 사용자 알림을 탐지 과정에서 모두 처리하면 후속 작업이 끝날 때까지 탐지가 지연될 수 있다. Queue를 이용해 이벤트 처리를 분리함으로써 이러한 영향을 줄일 수 있도록 구성했다.

### 공격 상태 관리와 반복 알림 제어

Event Handler는 캡처 세션별로 최근 1초 동안 발생한 `ATTACK` 후보를 집계한다. 공격 확정 조건을 만족하면 정상 상태에서 공격 상태로 전환하고, 이 전환 시점에 공격 기록과 최초 알림을 생성한다. `WARNING` 결과 자체를 사용자 경보나 공격 기록으로 남기지는 않는다.

공격 기록인 `AttackRecord`에는 발생 시각, 캡처 세션 식별자인 `source_id`, BSSID 그룹을 나타내는 `group_key`를 저장한다. Detector의 점수와 근거 데이터는 입력 결과에 포함되지만 현재 공격 기록에는 저장하지 않는다.

공격 상태가 유지되는 동안에는 마지막 알림으로부터 5초 이상 지난 `ATTACK` 후보가 들어왔을 때 반복 알림을 생성한다. 공격 확정 조건이 마지막으로 성립한 뒤 5초 이상 지나서 새 결과를 처리하면 기존 공격 상태를 해제한 뒤 그 결과를 평가한다. 입력이 없는 동안 타이머가 따로 알림을 발생시키는 구조는 아니다.

사용자에게 전달하는 알림은 공격 탐지 사실과 네트워크 연결 상태 확인을 안내하는 고정 문구다. Event Handler가 `NotificationEvent`를 Notification Bridge에 전달하면, Bridge가 사용자 세션의 D-Bus를 통해 데스크톱 알림으로 변환한다. Desktop UI는 별도로 저장된 공격 기록을 읽어 화면에 표시한다.

### 구성요소 오류 처리

공격 이벤트 외에 시스템 구성요소의 오류도 처리하도록 구현했다. 패킷 수집이나 탐지 모듈에서 치명적인 오류를 나타내는 `ComponentFailure` 이벤트가 전달되면 오류 발생 위치와 진단 메시지를 기록하고, 감시 기능이 중단되었음을 사용자에게 알린 뒤 감시 종료를 요청하도록 했다.

공격이 탐지되지 않는 상황과 감시 기능 자체가 정상적으로 동작하지 않는 상황을 구분해 전달하는 것도 Event Handler의 역할이었다.

## 5. 검증 결과와 한계

팀에서는 AWID3 데이터를 기반으로 단계별 파라미터 탐색을 수행했다. Window와 Burst 설정, 상태 임계값, 공격 후보 수 기준을 세 단계로 나누어 총 343회의 후보 평가를 진행했다. 이후 AWID3 Test Set의 1,036개 Window를 대상으로 평가한 결과는 다음과 같다.

| 지표               | 결과  |
| ---------------- | --- |
| TP — 공격을 공격으로 탐지 | 109 |
| TN — 정상을 정상으로 판정 | 927 |
| FP — 정상을 공격으로 오탐 | 0   |
| FN — 공격을 놓친 경우   | 0   |
| Precision        | 1.0 |
| Recall           | 1.0 |
| F1-Score         | 1.0 |

해당 테스트에서는 FP와 FN이 발생하지 않았다. 다만 이 결과만으로 모든 환경에서 완벽하게 탐지한다고 볼 수는 없다. 정상과 공격 데이터의 불균형이 있고, 탐지 규칙이 AWID3 환경에 맞춰졌을 가능성도 있어 추가 검증이 필요하다.

현재 DART는 Deauthentication 공격의 Burst 패턴에 특화되어 있다. 정상적인 Deauthentication 사례가 부족한 데이터에서 평가했으므로, 실제 환경의 정상 연결 종료에 대한 오탐 성능은 추가로 확인해야 한다. 다양한 AP와 클라이언트, PMF 활성 여부에 따른 동작 차이를 확인할 필요가 있다. 여러 채널을 감시하려면 채널 호핑이나 다중 인터페이스도 고려해야 한다.

## 6. 프로젝트 결과와 돌아본 점

DART는 Kali Linux에서 설치할 수 있도록 `.deb` 패키지 빌더와 서비스 설정, 앱 실행 구성을 갖추었다. Monitor Mode 인터페이스와 채널을 설정한 뒤 Desktop UI에서 감시를 시작하면, 시스템 데몬이 패킷 수집과 탐지를 수행하고 사용자는 공격 기록과 데스크톱 알림을 확인할 수 있다.

이번 프로젝트에서 내가 맡은 부분은 **탐지 후보를 집계해 공격 상태를 관리하고, 그 결과를 기록과 사용자 알림으로 연결하는 과정**이었다. Event Handler를 구현하면서 탐지 기능뿐 아니라 결과 전달, 로그 기록, 오류 처리도 함께 설계되어야 한다는 점을 배울 수 있었다.

특히 Queue를 통한 비동기 처리와 계층별 역할 분리를 실제 프로젝트에 적용해 볼 수 있었다. 앞으로는 이벤트가 짧은 시간에 많이 발생하거나 로그와 UI 처리가 느려지는 상황에서도 안정적으로 동작하는지 확인하며, 이벤트 처리 구조에 대한 이해를 더 넓혀가고 싶다.
