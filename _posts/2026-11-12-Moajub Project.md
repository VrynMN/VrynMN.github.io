## 개요

교내 분실물 웹 서비스 모아줍에서 내가 맡은 등록 기능의 개발 과정을 정리했다. 개발 중 발생한 오류를 해결한 과정과 팀 협업에서 배운 점을 담았다.

</div>

## 모아줍 프로젝트

교내에서 물건을 잃어버리면 분실물 공지가 어느 학과 단체 채팅방에 올라왔는지 몰라 찾기 어려울 때가 있다. 이런 불편을 줄이기 위해 교내 곳곳에 흩어진 분실물 정보를 한곳에 등록하고 찾아볼 수 있는 웹 서비스 모아줍을 개발했다.

백엔드는 Python과 Flask, 화면은 HTML/CSS/JavaScript로 구현했고, 게시글은 PostgreSQL에 저장했다. 팀에서 나는 분실물 등록 기능을 맡았다. 등록 화면을 만들고, 사용자가 입력한 값을 검증한 뒤 게시글 삭제용 비밀번호를 해싱해 등록 정보를 데이터베이스에 저장하도록 구현했다.

## 제보형과 습득형 등록 폼 만들기

분실물 정보를 등록하는 상황을 두 가지로 나눴다. 학과 단톡방의 분실물 공지를 보고 정보를 공유하는 경우는 제보형, 물건을 직접 주운 경우는 습득형이다.

두 유형 모두 날짜와 시간, 물건 이름, 특징을 입력한다. 다만 제보형에는 공지를 본 단톡방 이름이 필요하고, 습득형에는 습득 장소와 보관 위치가 필요하다. 그래서 JavaScript의 `updateType()`에서 현재 선택한 유형을 확인하고, 필요한 입력칸만 보여주도록 했다. 날짜와 시간의 제목도 유형에 맞춰 '안내' 또는 '습득'으로 바꿨다.

여기서 신경 쓴 부분은 숨긴 입력칸의 처리였다. 화면에서만 숨기면 필수 입력 검사나 폼 제출에 여전히 영향을 줄 수 있다. 그래서 사용하지 않는 입력칸은 숨기는 동시에 비활성화해 검증과 제출 대상에서 제외했다. 화면은 기존 헤더와 공통 `style.css`를 재사용했다.

## 비밀번호 검증은 브라우저와 서버에서 각각 처리

게시글을 나중에 삭제할 때 사용할 비밀번호는 숫자 4자리로 받았다. 처음에는 형식이 틀리면 같은 문구를 보여줬지만, 이후에는 비밀번호를 입력하지 않은 경우, 숫자가 아닌 문자가 섞인 경우, 길이가 4자리가 아닌 경우를 나눠 안내했다.

브라우저에서는 `validatePassword()`가 입력값을 확인하고, `setCustomValidity()`로 오류 메시지를 설정한다. 사용자가 값을 수정하면 다시 검사하고, 정상 값이면 기존 오류를 해제한다. 서버에서도 같은 조건을 확인한다. 브라우저 검사는 사용자가 오류를 바로 알아차리게 하는 데 유용하지만, 브라우저를 거치지 않고 서버에 요청할 수도 있기 때문이다.

비밀번호는 정수로 변환하지 않고 문자열로 처리했다. 그래야 `0123`처럼 앞자리가 0인 값도 그대로 검증할 수 있다. 터미널에서 Flask 테스트 클라이언트로 등록 요청을 보내 `0123`은 통과하고, 3자리·5자리·문자·공백이 포함된 값은 서버에서도 거부되는 것을 확인했다.

## 화면의 '완료' 메시지 대신 실제 해시 검증하기

비밀번호 원문을 DB에 남기지 않기 위해 bcrypt로 해시를 생성했다. 입력값 검증을 모두 통과한 뒤에만 해싱하고, `bcrypt.gensalt()`로 매번 새로운 salt를 만들어 같은 비밀번호라도 서로 다른 해시가 나오도록 했다.

개발하면서 화면의 '해싱 완료' 메시지만으로는 실제로 해시가 만들어졌는지, 그 해시로 비밀번호를 확인할 수 있는지 판단하기 어려웠다. 그래서 PowerShell에서 `python -`로 테스트 코드를 실행했다. Flask 테스트 클라이언트의 `client.post()`로 등록 처리 코드를 실행하고, 생성된 해시를 `bcrypt.checkpw()`로 확인했다. 원래 비밀번호는 통과하고 다른 비밀번호는 실패했으며, 같은 비밀번호로 만든 두 해시도 서로 달랐다.

실패 상황도 확인했다. `unittest.mock.patch`로 테스트 중에만 해싱 함수가 예외를 발생시키도록 바꾼 뒤, 서버가 오류를 안내하고 성공 처리를 하지 않는지 검사했다. 이 단계에서는 해싱과 오류 처리를 확인했고, 실제 DB에 해시가 저장되는지는 다음 단계에서 따로 확인했다.

## DB 저장을 연결하면서 생긴 오류

검증과 해싱을 마친 뒤에는 `storage.py`의 `save_item()`을 호출하도록 연결했다. 이 함수는 제보형이면 `ReportItem`, 습득형이면 `FoundItem`을 만들고, 게시글 정보와 비밀번호 해시를 저장한다. 등록 요청을 처리하는 `register()`와 DB 저장을 담당하는 `save_item()`을 분리해, 요청과 응답 흐름을 보면서 저장 세부 코드까지 한꺼번에 읽지 않아도 되도록 했다.

처음 저장을 연결했을 때는 웹페이지에 “저장 중 오류가 발생했습니다”라는 안내가 떴다. 로그에 실패한 테이블명과 컬럼명을 남겨 확인해 보니, 문제는 `report_items.password_hash`였다. 저장 코드를 연결하는 과정에서 해싱 단계가 빠져, 해시가 들어가야 할 변수에 초기값인 `None`이 그대로 남아 있었다. DB에서는 해당 컬럼에 `NULL`을 허용하지 않으므로 저장을 거부한 것이다.

해결 방법은 검증 → 해싱 → 저장 순서를 복구하는 것이었다. 해싱이 성공했을 때만 `save_item()`을 호출하도록 수정했다. 이후 제보형과 습득형을 웹페이지에서 각각 등록하고, 실제 DB를 조회해 입력 정보가 저장됐는지 확인했다. 저장된 해시는 원래 비밀번호로 `checkpw()`를 실행해 검증했다.

저장에 성공하면 `303` 응답으로 목록을 다시 열도록 했다. 등록은 `POST`로 처리하지만 이동한 목록은 `GET`으로 열리므로, 목록을 새로고침해도 같은 등록 요청이 다시 보내지지 않는다. 저장에 실패하는 경우는 임시 DB에서 오류를 강제로 발생시켜, 실패한 게시글이 남지 않고 롤백 후 다시 저장할 수 있는지 확인했다.

## 개발을 마치며

이번 프로젝트에서 가장 크게 배운 점은 화면에서 보이는 결과와 서버에서 실제로 처리된 결과를 각각 확인해야 한다는 것이다. 화면에 해싱 완료 메시지가 떠도, 생성된 해시로 비밀번호를 검증할 수 있는지는 별도로 확인해야 했다. 데이터베이스 저장도 마찬가지였다. 등록 후 목록으로 이동하는 것만 확인하는 데서 그치지 않고, 데이터베이스에 저장된 게시글과 비밀번호 해시를 직접 조회해 등록 과정이 끝까지 제대로 동작하는지 확인했다.

또한 GitHub로 협업하는 과정도 처음부터 끝까지 경험했다. 등록 기능을 이슈 단위로 나누고, 브랜치에서 작업한 뒤 PR을 올려 리뷰를 거쳐 병합했다. 리뷰 과정에서 중복 저장 코드를 발견해 수정했고, 병합 중 발생한 충돌도 해결했다. 다음 프로젝트에서는 이 경험을 바탕으로 작업 범위를 나누고 팀원들과 변경 사항을 공유하는 방식을 더 수월하게 정할 수 있을 것 같다.
