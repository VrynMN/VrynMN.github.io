## 취약점을 찾는 도구가 공격 통로가 된 이유 — Trivy 공급망 공격

개발팀이 평소처럼 보안 검살르 실행했다. 검사 결과도 정상적으로 나왔다. 그런데 그 검사를 실행하는 동안, 변조된 도구가 개발 환경에 저장된 비밀정보를 수집하고 있었다. 2026년 3월에 발생한 Trivy 공급망 공격은 이런 방식으로 피해를 일으켰다.

Trivy는 프로그램에 알려진 취약점이 있는지 검사하는 오픈소스 도구다. 개발팀은 보통 코드를 수정하거나 새 버전을 배포할 대 검사가 자동으로 실행되도록 설정한다. 이런 자동화 과정을 CI/CD라고 한다.

이번 사건에서는 공격자는 Trivy를 사용하는 기업에 하나씩 침입하는 대신, 기업들이 공통으로 사용하는 도구의 공식 배포 경로에 악성 코드를 넣었다. 이렇게 제품이나 도구를 공급하는 쪽을 침해해 그 사용 조직에까지 영향을 미치는 것을 공급망 공격이라고 한다.


## 사건 타임라인

| 날짜 (UTC)         | 주요 사건                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| **2026년 2월 27일** | 공격자가 Trivy의 GitHub 자동화 설정을 악용해 접근에 필요한 토큰 등 비밀정보를 탈취했다. 다른 저장소와 조직에도 접근했고, 악성 VS Code 확장 프로그램을 배포했다.             |
| **3월 1일**        | Trivy 팀이 악성 확장 프로그램을 내리고 침해를 확인한 계정의 자격증명을 폐기했다. 같은 날 공격자는 다른 침해 계정을 통해 활동을 이어갔다.                                |
| **3월 19일**       | 공격자가 3월 1일에 관측된 토큰으로 공식 배포 절차를 실행해 악성 Trivy `v0.69.4`를 배포했다. Trivy를 자동으로 설치하거나 실행하는 GitHub Actions의 버전 태그도 변조됐다. |
| **3월 22일**       | 또 다른 GitHub 조직에서 침해 활동이 확인됐다. 공격자는 유출된 자격증명으로 DockerHub에 악성 `0.69.5`와 `0.69.6` 컨테이너 이미지를 올렸다.                    |
| **3월 23일 이후**    | Trivy 팀은 DockerHub의 악성 태그를 제거하고 추가 조사와 보완을 진행했다. 최종 보고서 작성 시점까지 추가 의심 활동은 관측되지 않았다.                              |


## 처음 대응했는데 공격이 계속된 이유

토큰은 로그인 비밀번호처럼 시스템에 접근하거나 작업을 실행할 권한을 주는 값이다. 당시 Trivy는 여러 프로젝트에서 권한이 큰 자동화 계정을 사용하고 있었다. 공격자가 이런 계정의 토큰을 얻으면, 처음 침해한 저장소를 넘어 그 계정이 접근할 수 있는 다른 저장소와 배포 환경으로도 이동할 수 있었다.

Trivy 팀은 3월 1일에 침해가 확인된 계정의 토큰을 폐기했다. 하지만 공격자는 이미 다른 계정의 자격증명도 확보한 상태였다. 그 계정의 토큰이 살아 있었고, 3월 19일에 악성 버전을 공식 경로로 배포하는 데 쓰였다. 초기 조사가 처음 문제가 발견된 GitHub 조직에 집중됐다는 점도 영향을 줬다. 여러 프로젝트와 조직이 같은 계정이나 비밀정보를 공유하고 있었기 때문에, 어떤 계정이 침해됐는지와 그 계정이 어디까지 접근할 수 있었는지를 함께 확인해야 했다.


## 사용자는 왜 변조된 코드를 실행했을까?

일부 개발팀은 자동 검사에서 Trivy를 실행할 때 버전 태그를 사용했다. 태그는 특정 코드에 붙인 이름이다. 예를 들어 자동 검사에 v1이라고 적어 두면, 실행할 때 v1이 가리키는 코드를 불러온다. 

공격자는 이 태그가 악성 코드가 포함된 버전을 가리키도록 바꿨다. 그래서 사용자가 자신의 검사 설정을 한줄도 바꾸지 않았는데도, 다음 검사에서 변조된 코드가 실행될 수 있었다. 공식 경로에 올라온 Trivy v0.69.4 실행 파일에도 악성 코드가 들어 있었다.

악성 코드는 검사 작업이 실행되는 환경에서 GitHub 토큰, SSH 키, 클라우드 접속 키 등을 찾아 외부로 보내려 했다. 변조된 실행 파일은 평소처럼 취약점 검사도 수행했다. 화면에 정상적인 검사 결과가 나왔기 때문에 사용자가 결과만 보고 이상을 알아차리기는 어려웠다.


## 실제 피해 사례

### 1. CI/CD에서 탈취된 AWS 키가 클라우드 접근에 쓰였다

Kudelski Security 조사팀은 AWS의 활동 기록인 CloudTrail을 확인해 공격자가 계정 권한과 저장소를 조사한 흔적을 찾았다. 총 24개의 S3 버킷이 조사 대상이 됐다. S3 버킷은 AWS에서 파일을 담아 두는 공간이다.

당시 조직은 버킷 목록이나 권한 설정을 조회한 기록은 남기고 있었지만, 버킷 안의 파일을 읽은 기록은 수집하지 않았다. 그래서 공격자가 버킷을 살펴본 사실을 확인했지만, 실제로 파일을 내려받았는지는 확인할 수 없었다.

### 2. 자동 업데이트가 악성 컨테이너 이미지를 배포했다

이 조직은 `latest` 태그를 사용해 가장 최근에 배포된 Trivy 컨테이너 이미지를 자동으로 설치하고 있었다. 공식 배포 경로에 악성 이미지가 올라오자 자동 업데이트가 이를 받아 실행했다.

당시 엔트포인트 탐지/대응 도구인 EDR에는 악성 파일의 실행 기록이 남았지만 경보는 발생하지 않았다. 조사팀은 공개된 악성 파일 해시를 조직의 컨테이너 이미지 목록과 대조해 감염을 확인했다. 변조된 실행 파일에는 일부 환경에서 실행이 끝난 뒤에도 악성 코드가 동작하도록 설정을 남기는 기능이 있었다. 이 기능은 파일 분석에서 확인됐고, 피해 환경에서 실제로 지속적인 접근이 이루어졌는지는 별도로 확인해야 한다.


## Trivy 팀의 대응

Trivy 팀은 관련 GitHub 토큰과 배포 서비스의 토큰을 폐기했다. 기존 접근 권한이 해제됐는지 확인한 뒤 새 자격증명을 발급했고, 각 계정에 필요한 권한만 줄 수 있도록 전환 작업도 시작했다.

공식 배포 절차도 바꿨다. 처음 공격에 악용된 자동화 설정을 제거하고, 잘못된 설정을 자동으로 찾아내는 검사를 추가했다. 지원되는 배포 서비스에서는 공개한 릴리스를 나중에 변경하기 어렵도록 설정했다. 전담팀이 GitHub와 배포 서비스의 활동 기록을 살피고, 공개된 파일에 예상치 못한 변경이 생기면 확인하는 체계도 도입했다.


## Trivy를 사용하는 조직이 보완할 수 있는 것

Trivu 공급망 공격의 영향을 확인하려면 먼저 실행 기록을 살펴봐야 한다. GitHub Action을 통해 실행했는지, 실행 파일을 직접 설치했는지, 컨네이터 이미지를 받아 사용했는지에 따라 영향을 받은 버전과 시점이 달랐기 때문이다. 악성 버전을 실행했다면 해당 버전을 제거하고, 실행 당시 접근할 수 있었던 키와 토큰을 폐기하거나 교체해야 한다. 이후 GitHub와 클라우드의 감사 로그를 확인해 해당 자격증명이 사용된 흔적이 있는지도 조사한다. 

같은 문제가 반복되는 것을 막으려면 검증한 코드와 이미지를 고정해 사용하는 방법이 있다. GitHub Actions에서는 코드의 고유 식별자인 커밋 SHA를, 컨테이너에서는 이미지의 고유 식별자인 다이제스트를 사용한다. 이렇게 하면 버전 태그나 다른 코드나 이미지를 가리키도록 바뀌어도 기존에 지정한 버전이 실행된다.

검사 작업과 배포 작업의 권한도 분리할 필요가 있다. 취약점 검사에 배포용 AWS 키가 필요하지 않다면, 해당 키는 배포 작업에서만 사용할 수 있게 설정하면 된다. 민감한 파일을 보관하는 S3 버킷에는 파일 읽기 기록도 남겨 두는 게 좋다. 사고가 발생했을 때 버킷 목록만 조회했는지, 실제 파일에 접근했는지 구분할 수 있기 때문이다.

이 사건을 보면서 취약점 검사 작업이 왜 배포용 AWS 키까지 읽을 수 있었는지 생각해 보게 됐다. 검사와 배포를 같은 자동화 과정에서 실행하더라도 두 작업에 필요한 권한은 다르다. 검사 과정에서 쓸 수 있는 키를 줄여 두었다면, 잘못된 버전이 실행됐을 때도 피해가 클라우드까지 번질 가능성을 줄일 수 있었을 것이다.
