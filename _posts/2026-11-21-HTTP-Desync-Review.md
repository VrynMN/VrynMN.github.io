## 논문 선정 이유

네트워크 분야에 관심이 있어 실제 웹 통신 과정에서 발생하는 보안 문제를 다룬 논문을 선택했다. 특히 프록시와 서버가 같은 HTTP 메시지를 다르게 해석하면서 취약점이 발생한다는 점이 흥미로웠다. 또한 이러한 차이를 자동으로 찾는 HDHunter를 제안하고 실제 HTTP 구현체에서 효과를 평가했다는 점도 선택 이유였다. 이 논문을 통해 HTTP 통신 구조를 더 깊이 이해하고, 네트워크 지식이 보안 취약점 분석과 테스트 도구 설계에 어떻게 활용되는지 배우고자 했다.

## 논문 읽기 전 정리한 문제의식

이 논문이 다루는 문제는 같은 HTTP 메시지를 프록시와 서버가 서로 다르게 해석하면서 발생하는 HTTP Desync이다. 예를 들어 프록시는 하나의 요청이라고 판단한 데이터를 백엔드 서버는 두 개의 요청으로 해석할 수 있다. 이 차이를 악용하면 공격자는 프록시의 검사를 통과한 메시지 안에 별도의 요청을 숨길 수 있다.

이 문제가 중요한 이유는 실제 웹 서비스가 하나의 서버만으로 동작하지 않기 때문이다. 사용자의 요청은 CDN, reverse proxy, 웹 서버, 애플리케이션 서버 등 여러 구성 요소를 거칠 수 있다. 각 구성 요소가 개별적으로 정상 동작하더라도, 서로 다른 해석 기준으로 연결되면 전체 시스템에서 보안 문제가 발생할 수 있다.

논문에서 주요 비교 대상으로 다룬 Smuggler, T-Reqs, HDiff는 사전 정의된 입력이나 black-box 방식의 테스트를 사용했다. 저자들은 이러한 방식이 구현체 내부의 실행 정보를 활용하지 못하고 주로 요청 측 문제에 집중한다는 한계를 지적했다. 따라서 새로운 처리 경로를 찾아가는 데 한계가 있었고, 요청 측 문제에 집중하여 HTTP 응답과 CGI 응답에서 발생하는 문제를 충분히 다루지 못했다.

## 서버 하나의 문제가 아니라 서버 사이의 문제

처음에는 HTTP 요청을 검사하는 프록시가 있으면 위험한 요청을 어느 정도 차단할 수 있다고 생각했다. 그러나 이 논문은 검사하는 쪽과 실행하는 쪽이 같은 메시지를 다르게 이해한다면 검사 자체가 무력화될 수 있다는 문제를 보여준다.

HTTP/1.1에서는 하나의 TCP 연결로 여러 메시지를 주고받을 수 있다. 따라서 각 구현체는 어디까지가 현재 메시지이고 어디부터가 다음 메시지인지 정확하게 판단해야 한다. 이때 본문 길이를 나타내는 Content-Length와 전송 인코딩을 나타내는 Transfer-Encoding 등의 처리가 중요하다.

만약 프록시와 백엔드가 메시지 경계를 다르게 판단하면 프록시는 정상 요청 하나를 전달했다고 생각하지만, 백엔드는 그 안에서 추가 요청을 발견하여 처리할 수 있다. 이것이 HTTP Request Smuggling의 기본 원리다.

이 논문의 저자들은 이러한 문제를 HTTP Request Smuggling에만 한정하지 않았다. 메시지의 개수, 내용, 순서가 달라지는 경우로 나누고, 요청뿐 아니라 응답에서도 같은 문제가 발생할 수 있다고 보았다. 이 관점에서 논문의 출발점은 새로운 공격 입력 하나를 찾는 것이 아니라, 여러 구현체 사이의 해석 차이를 체계적으로 발견하는 방법을 만드는 것이다.

프록시는 Transfer-Encoding을 기준으로 전체 데이터를 하나의 요청으로 처리하지만 백엔드는 Content-Length를 기준으로 다른 위치에서 요청을 나눈다. 이 차이로 인해 프록시가 별도 요청으로 인식하지 못한 내용이 백엔드에서는 추가 요청으로 처리될 수 있다.

## 해석 차이를 자동으로 찾는 HDHunter

논문에서 제안한 HDHunter의 핵심은 동일한 입력을 두 HTTP 구현체에서 실행하고, 내부 실행 정보와 처리 상태를 함께 비교하는 것이다.

이를 위해 두 가지 테스트 방식을 결합했다. 첫 번째는 내부 정보를 일부 활용하는 gray-box fuzzing이다. 입력에 의해 코드의 어느 부분이 실행되었는지를 나타내는 coverage를 활용하여 새로운 실행 경로를 탐색한다. 두 번째는 동일한 입력을 여러 구현체에 넣어 차이를 찾는 differential testing이다. 쉽게 말하면 입력을 무작정 바꾸기보다, 새로운 처리 경로를 실행하는 입력을 찾아가면서 두 구현체가 무엇을 다르게 이해했는지 확인하는 방식이다.

### HDHunter의 동작

1. 실제 네트워크 트래픽에서 HTTP 메시지를 추출하여 초기 입력인 seed를 준비한다
2. 메시지 순서, 메시지 구성 요소, 바이트 수준에서 입력을 변형한다
3. 변형한 입력을 두 구현체에서 실행한다
4. 실행 coverage와 메시지 처리 상태를 수집한다
5. 두 구현체 사이의 불일치를 탐지하고, 탐색에 유용한 입력을 다음 테스트에 활용한다
6. 발견한 불일치를 사람이 분석하여 실제 취약점으로 이어지는지 확인한다

![그림 2]({{ '/assets/img/Pasted image 20261120192510.png' | relative_url }})

HDHunter는 변형한 입력을 두 구현체에서 실행하고, 실행 coverage와 메시지 처리 상태를 수집한다. 여기서 coverage는 다음에 어떤 입력을 더 탐색할지 결정하는 데 사용하고, 처리 상태는 메시지 개수, 소비한 데이터 길이, 본문 내용, 순서 등의 불일치를 판별하는 데 사용한다. 탐지한 불일치는 수동 분석을 거쳐 실제 취약점으로 이어지는지 확인한다.

또한 HTTP Desync 테스트는 이전 테스트의 연결 상태나 남은 데이터에 영향을 받을 수 있다. 저자들은 이를 해결하기 위해 snapshot 기반 executor를 사용했다. 대상이 준비된 상태를 저장하고 각 테스트 후 해당 상태로 복원하여, 매번 전체 서버를 재시작하지 않고도 깨끗한 환경에서 반복 실행할 수 있게 했다.

이 설계에서 인상적이었던 점은 입력 생성뿐 아니라 차이를 판정하는 방법과 테스트 환경의 상태 관리까지 함께 해결했다는 것이다. 네트워크 프로그램을 제대로 테스트하려면 어떤 데이터를 보낼지만큼 어떤 상태에서 실행할지도 중요하다는 것을 알 수 있었다.

## 실제 취약점 발견과 설계의 효과

저자들은 통합 서버, 캐시 서버, 네트워크 프레임워크, 애플리케이션 서버를 포함한 오픈소스 HTTP 구현체 19개를 평가했다. HTTP 요청 테스트 쌍 171개, HTTP 응답 36개, CGI 응답 10개를 구성하고, 각 테스트 쌍을 12시간씩 5회 반복했다.

그 결과 Apache, Tomcat, Squid 등을 포함한 구현체에서 새로운 HTTP Desync 취약점 17개를 발견했고, 9개의 CVE ID를 부여받았다. 이는 단순히 두 프로그램의 출력이 다르다는 사실을 찾는 데 그치지 않고, 실제 보안 영향을 확인했다는 점에서 의미가 있다.

발견한 문제에는 비표준 숫자 파싱, trailer section 처리, 줄 구분자 해석, TE와 CL 헤더 처리 방식의 차이 등이 있었다. 이들은 메시지의 경계나 내용을 다르게 해석하게 하여 요청 밀수, 요청 내용 혼동, 응답 탈취, 응답 위조로 이어질 수 있었다.

특히 응답 탈취 사례가 인상적이었다. Twisted에서 pipelining된 요청들의 응답 순서가 어긋날 수 있었고, 논문에서 구성한 조건에서는 공격자가 이를 이용해 피해자에게 전달되어야 할 응답을 받을 수 있었다. 보안 문제를 요청이 들어오는 방향에만 한정하면 중요한 공격 가능성을 놓칠 수 있다는 것을 보여주는 사례였다.

(a)는 요청 밀수, (b)는 요청 내용 혼동, (c)는 응답 탈취, (d)는 응답 위조를 보여준다. 이는 구현체 간 해석차이가 단순한 동작 차이를 넘어 실제 보안 문제로 이어질 수 있음을 보여준다.

저자들은 기존 도구인 T-Reqs와 HDiff와도 비교했다. 평가에서 두 도구는 일부 불일치를 발견했지만, HDHunter는 기존 도구가 놓친 유형도 탐지했다. 또한 coverage 비교에서 더 많은 실행 경로를 탐색했다.

설계 요소를 교체하는 ablation study도 수행했다. Apache-NGINX 조합에서 HDHunter의 입력 생성기를 AFL의 기본 방식으로 교체하자 실행 속도가 약 120회/초에서 13회/초로 떨어졌다. 저자들은 불완전한 입력이 많이 생성되어 timeout이 발생한 것을 원인으로 설명했다. Snapshot 방식도 전체 재시작 방식보다 Apache-Squid에서 약 52배, Apache-Tomcat에서 약 88배 빠른 실행 성능을 보였다. 내가 평가 근거로 주목한 것은 ablation study다. 완성된 도구끼리 비교하는 데 그치지 않고 구성요소를 교체하여 성능 변화를 확인했기 때문에, HTTP 구조를 고려한 입력 생성과 snapshot 방식이 왜 필요한지 이해할 수 있었다.

이 결과를 통해 HTTP 구조를 고려한 입력 생성과 빠른 상태 복원이 실제 테스트 효율에 기여했음을 확인할 수 있다. 다만 더 높은 coverage, 더 빠른 실행, 더 많은 취약점 발견은 구분하여 평가해야 한다. 실행 경로가 늘었다는 사실만으로 모든 취약점을 더 찾는다고 단정할 수는 없으며, 실제 공격 사례와 함께 해석해야 한다고 생각한다.

## 결과의 한계와 아쉬운 점

 첫 번째 한계는 소스 코드와 내부 상태에 접근해야 한다는 점이다. HDHunter는 내부 계측을 활용하므로 외부에 공개된 웹사이트나 폐쇄형 서비스를 그대로 검사하는 도구로 사용하기 어렵다. 따라서 적용 대상은 주로 오픈소스 구현체를 다루는 개발자와 보안 연구자라고 볼 수 있다.
 
 두 번째는 현재 설계가 HTTP/1.1에 맞춰져 있다는 점이다. HTTP/2와 HTTP/3에 적용하려면 입력 구조와 탐지 방식을 수정해야 한다. 특히 HTTP/2에서 HTTP/1.1로 변환되는 구간은 서로 다른 프로토콜의 해석 기준이 만나는 지점이므로 추가 연구 가치가 있다고 생각한다.

 세 번째는 수작업 부담이다. 내부 상태 수집용 코드를 삽입해야 하며, 발견된 불일치가 실제 공격으로 이어지는지도 사람이 분석해야 한다. 따라서 자동화된 탐색 도구이지만, 취약점 검증 전체가 자동화된 것은 아니다.

 내가 추가로 확인하고 싶은 부분은 실제 운영 환경에 대한 일반화 가능성이다. 논문은 coverage 수집의 변동을 줄이기 위해 단일 스레드 환경에서 평가했다. 그러나 실제 서비스는 여러 작업자와 동시 요청, 다양한 연결 재사용 정책을 사용한다. 같은 불일치가 운영 구성에서도 동일한 보안 영향으로 이어지는지를 별도로 확인할 필요가 있다.

 또한 논문에서 사용한 버전과 조건에서 발견한 결과를 해당 소프트웨어를 사용하는 모든 서비스의 취약성으로 확대해서는 안 된다. 실제 공격 가능성은 프록시의 정제 여부, upstream 구성, 지속 연결과 pipelining 설정 등에 따라 달라질 수 있다.

## 내가 배운 점과 이 논문이 남긴 것

이 논문을 통해 가장 크게 배운 것은 개별 구성 요소의 안전성이 전체 시스템의 안전성을 보장하지는 않는다는 점이다. 프록시와 서버가 각각 나름의 기준으로 동작하더라도, 같은 데이터를 서로 다르게 해석하면 그 사이에 공격 경로가 생길 수 있다.

논문의 기여는 취약점 17개를 발견했다는 성과뿐 아니라, 해석 차이를 찾기 위해 입력 생성, 내부 상태 비교, 실행 환경 복원을 하나의 시스템으로 구성했다는 데 있다고 생각한다. 요청뿐 아니라 응답과 CGI 변환까지 살펴보았다는 점도 웹 시스템을 더 넓게 바라보게 한다.

보안 테스트를 할 때도 단순히 프로그램이 중단되는지 확인하는 것을 넘어, 연결된 구성 요소들이 같은 데이터를 같은 의미로 처리하는지 확인해야 한다는 관점을 얻었다. 이는 네트워크와 클라우드 시스템을 공부하거나 프로젝트를 진행할 때에도 적용할 수 있는 문제의식인 것 같다.

## 앞으로 이어서 해볼 것

먼저 논문의 비교 대상인 `T-Reqs: HTTP Request Smuggling with Differential Fuzzing`을 추가로 읽고 싶다. HDHunter와 입력 생성 방식, 내부 정보 활용 여부, 불일치 판정 기준을 비교하면 gray-box 접근이 무엇을 개선했는지 더 분명하게 이해할 수 있을 것 같다.

직접 재현할 부분으로는 논문의 Apache Traffic Server-gevent 요청 밀수 사례를 선택하고 싶다. 격리된 로컬 환경에 논문의 버전과 설정을 구성하고, 프록시와 백엔드가 동일한 입력의 경계를 어떻게 다르게 인식하는지 확인하고 싶다. 이후 수정 버전과 설정을 비교하여 공격이 차단되는 조건을 살펴볼 계획이다. 

재현 과정에서는 공격 성공 여부뿐 아니라 다음 항목을 함께 기록할 계획이다.

- 각 구성 요소가 인식한 메시지 개수와 경계
- 요청 정제 전후의 차이
- 연결 재사용 설정에 따른 결과 변화
- 수정 전후의 처리 방식 차이

프로젝트로 발전시킨다면 프록시-백엔드 조합의 HTTP 해석 일관성을 검사하는 작은 회귀 테스트 도구를 만들고 싶다. 서버나 프록시 업데이트 전후에 정해진 테스트 입력을 실행하여 새롭게 생긴 처리 차이를 알려주는 방식이다. 처음부터 모든 HTTP Desync를 탐지하기보다 trailer 처리 같은 한 유형으로 범위를 좁혀 구현하고 검증하는 것이 현실적이라고 생각한다.

이 접근은 WAF와 애플리케이션 서버 사이의 입력 해석 차이를 검사하는 데에도 적용해볼 수 있을 것 같다. 예를 들어 같은 입력에 대한 URL decoding이나 매개변수 처리 결과가 달라지면 보안 검사를 우회할 가능성이 생길 수 있다. 다만 단순히 처리 결과가 다르다는 사실만으로는 취약점이라고 판단하지 않고, 실제 보안 정책 우회로 이어지는지를 확인하는 기준부터 정해야 한다고 생각한다.
